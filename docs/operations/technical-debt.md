# Технический долг инфраструктуры

Последнее обновление: **26 октября 2026 года**.

Задачи ниже выполняются отдельными небольшими изменениями после периода
наблюдения за миграцией. Не следует одновременно менять сетевую доступность,
Dockerfile, версии образов и секреты: это усложнит проверку и rollback.

## Приоритет 0 — безопасность

### Закрыть публичный PostgreSQL

Сейчас Compose публикует `5432:5432` на всех интерфейсах VPS. Если к базе не
подключаются внешние клиенты, секцию `ports` у `database` нужно удалить.
Directus продолжит обращаться к базе внутри Docker по `database:5432`.

Если прямой доступ администратора всё же нужен, порт следует привязать только
к loopback:

```yaml
ports:
  - "127.0.0.1:5432:5432"
```

Внешнее подключение тогда выполняется через SSH tunnel.

Готово, когда `ss -lntp` не показывает `0.0.0.0:5432` или `[::]:5432`, а
Directus и PostgreSQL проходят health-check.

### Ограничить остальные upstream-порты localhost

Порты `3020`, `8055` и `5050` сейчас также опубликованы на всех интерфейсах.
Поскольку внешний трафик идёт через Apache, их следует привязать к
`127.0.0.1`:

```yaml
ports:
  - "127.0.0.1:3020:3000"
```

Аналогично ограничиваются `8055:8055` и `5050:80`. Изменение нужно проверить
локальными `curl`, затем через все публичные домены.

### Ротировать раскрытые секреты

Если значения, использованные во время диагностики, были настоящими, нужно
заменить пароли и ключи PostgreSQL, Directus, SMTP и pgAdmin. Ротация должна
иметь отдельный порядок и проверенный способ возврата. Секреты остаются только
в серверном `.env` с правами `600`.

## Приоритет 1 — дисковое пространство и логи

### Очистить неактивный build cache

На момент фиксации Docker показывал около `3.04 GB` полностью неактивного build
cache. После завершения периода наблюдения его можно удалить командой:

```bash
docker builder prune -f
```

Команда не должна запускаться с `--volumes`. После очистки нужно сохранить
вывод `df -h /` и `docker system df`.

Не следует использовать общий `docker system prune --volumes`: production
volumes содержат базу, Directus uploads и данные pgAdmin.

### Ограничить размер Docker-логов

У сервисов нет ротации логов. Особенно многословен `parks-front`, который
сейчас выводит крупные объекты контента Directus.

Первый шаг — убрать ненужные `console.log` из frontend. Затем для каждого
сервиса добавить ограничение, например:

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
```

Изменение применяется после пересоздания контейнеров. Готово, когда
`docker inspect` подтверждает параметры логирования, а размер файлов в
`/var/lib/docker/containers` перестаёт неограниченно расти.

### Контролировать заполнение диска

До появления автоматического мониторинга периодически выполнять:

```bash
df -h /
docker system df
du -ah /var/lib/docker/containers | sort -rh | head -20
```

Желательно настроить предупреждение до достижения 80–85% заполнения.

## Приоритет 2 — надёжность deployment

### Перевести frontend в production-режим

Текущий Dockerfile запускает `next dev --turbopack`. Нужен multi-stage build с
`npm ci`, `next build` и `next start`, желательно с Next.js standalone output.
Это уменьшит размер и шум логов, уберёт dev-сервер из production и сделает
запуск воспроизводимым.

### Добавить health-check сервисам

Полноценный Docker health-check сейчас есть только у PostgreSQL. Следует
добавить проверки Directus и frontend; pgAdmin — если он остаётся постоянно
запущенным. `depends_on` должен ждать только действительно необходимых
сервисов.

### Автоматизировать обновление и smoke-check

После стабилизации оформить безопасный deploy-скрипт, который выполняет:

```text
git pull --ff-only
docker compose config --quiet
docker compose build parks-front
docker compose up -d --no-build
docker compose ps
локальные и публичные HTTP-проверки
```

Скрипт не должен автоматически удалять volumes, резервные копии или старые
образы до прохождения проверок.

### Автоматизировать резервные копии

Нужны регулярные PostgreSQL dumps и резервное копирование Directus uploads во
внешнее хранилище с контрольными суммами и периодической проверкой
восстановления. Единственная копия на том же VPS не считается достаточной.

## Приоритет 3 — уборка после стабилизации

- Архивировать старые Compose-файлы вне рабочих директорий VPS.
- Не удалять external volumes с production-данными.
- Проверить необходимость постоянного запуска и публичного домена pgAdmin.
- Устранить предупреждения Apache о повторной загрузке модулей и устаревшем
  `NameVirtualHost`; сейчас конфигурация при этом проходит `Syntax OK`.
- Решить отдельно, остаётся ли Apache на хосте или reverse proxy переносится в
  Compose/Caddy. Для интеграции «НЕДЕЛЬКИ» такой перенос не обязателен.
- Зафиксировать Directus schema snapshot в Git после создания коллекций
  лендинга.
